**Проект:** DataBridge — Конвертер и валидатор данных  
**Команда:** Групповой проект (DataBridge Team)  
**Дата:** Ноябрь 2026  
**Версия документа:** 1.0

## 1. Введение и бизнес-контекст

### 1.1. Проблема
Учебные отделы образовательных учреждений и малый бизнес сталкиваются с регулярной проблемой разнородности данных. Анкеты абитуриентов, списки студентов, ведомости успеваемости, клиентские базы и отчеты поступают в несвязанных между собой форматах: CSV с произвольными разделителями, выгрузки JSON из веб-форм, XML из государственных систем и таблицы Excel (.xlsx) от пользователей. 

Ручная выверка таких данных приводит к критическим ошибкам:
- Невалидные адреса электронной почты;
- Нарушение уникальности идентификаторов;
- Неверные форматы дат и выход значений за допустимые диапазоны;
- Ошибки типизации данных при импорте в целевые информационные системы.

### 1.2. Назначение системы
**DataBridge** — это консольная утилита (CLI), предназначенная для автоматизации конвейера обработки данных: пакетного чтения из поддерживаемых форматов, строгой валидации по декларативным правилам, очистки и трансформации значений, конвертации в целевой формат и генерации наглядных отчетов об ошибках и сводной аналитики.

## 2. Функциональные требования (MVP)

### 2.1. Подсистема чтения (Readers)
- **FR-1.1:** Чтение файлов формата **CSV** с поддержкой:
  - Заголовков в первой строке и файлов без заголовков (`col_1`, `col_2`, ...);
  - Настраиваемых разделителей (запятая, точка с запятой, табуляция, вертикальная черта) и автоопределения разделителя;
  - Корректной работы с экранированными полями и многострочными значениями в кавычках.
- **FR-1.2:** Чтение файлов формата **JSON**:
  - Массив объектов (`[ { ... }, { ... } ]`);
  - Объекты-обертки верхнего уровня (`{ "items": [ ... ] }`, `{ "data": [ ... ] }`).
- **FR-1.3:** Чтение файлов формата **XML**:
  - Плоские структуры списков записей (`<records><record>...</record></records>`);
  - Чтение как дочерних тегов, так и атрибутов элементов;
  - Автоматическое распознавание тегов записей.
- **FR-1.4:** Чтение файлов формата **Excel (.xlsx)**:
  - Чтение активного листа или листа по заданному имени (`--sheet`);
  - Извлечение типизированных значений ячеек без формульного мусора (`data_only=True`).
- **FR-1.5:** Автоматическое определение формата файла по расширению (`.csv`, `.json`, `.xml`, `.xlsx`), либо явное переопределение через параметры CLI.
- **FR-1.6:** Обязательное отслеживание номера исходной строки (`_row_number`) для каждой записи для точной локализации ошибок.

### 2.2. Подсистема валидации (Validators)
Валидация выполняется на основе декларативной схемы (в формате YAML или JSON).

- **FR-2.1: Обязательность поля (`required`)**  
  Проверка наличия поля и отсутствия пустого значения (`None`, пустая строка).
- **FR-2.2: Типизация (`type`)**  
  Поддержка проверки типов данных:
  - `integer`: целое число (строгое отсутствие дробной части);
  - `float`: вещественное число (с поддержкой точки и запятой в качестве разделителя);
  - `string`: строковое значение;
  - `date`: дата с настраиваемым шаблоном (например, `YYYY-MM-DD`, `DD.MM.YYYY`);
  - `boolean`: булево значение (`true`/`false`, `1`/`0`, `yes`/`no`, `да`/`нет`).
- **FR-2.3: Диапазоны (`min` / `max`)**  
  Проверка числовых значений и дат на принадлежность заданному интервалу.
- **FR-2.4: Регулярные выражения (`pattern`)**  
  Соответствие строки шаблону регулярного выражения (например, валидация e-mail, телефонных номеров, СНИЛС, ИНН).
- **FR-2.5: Уникальность (`unique`)**  
  Контроль уникальности значений поля в рамках всего набора данных (пакетный контекст).
- **FR-2.6: Длина строки (`min_length` / `max_length`)**  
  Ограничение минимальной и максимальной длины текстового поля.
- **FR-2.7: Допустимые значения (`allowed_values`)**  
  Контроль соответствия значения фиксированному списку (перечислению / enum).

### 2.3. Подсистема трансформации и конвертации (Converters)
- **FR-3.1: Конвертация между любыми форматами**  
  Любая пара (CSV ↔ JSON ↔ XML ↔ Excel).
- **FR-3.2: Маппинг полей (Field Mapping)**  
  Переименование колонок по правилу `mapping: { "old_name": "new_name" }` или свойству `alias` у поля.
- **FR-3.3: Встроенные трансформации** (минимум 3 по ТЗ, реализовано 7):
  1. `upper` / `uppercase` — перевод в верхний регистр;
  2. `lower` / `lowercase` — перевод в нижний регистр;
  3. `strip` / `trim` — удаление начальных и конечных пробелов;
  4. `capitalize` — капитализация первой буквы;
  5. `replace_map` / `dict_replace` — замена значений по словарю;
  6. `timestamp_to_date` — вычисление даты из Unix timestamp;
  7. `format_date` — переформатирование строки даты между форматами;
  8. `default` — значение по умолчанию при отсутствии или пустоте поля.
- **FR-3.4: Изоляция ошибочных данных**  
  Записи, не прошедшие валидацию, отфильтровываются из итогового набора и сохраняются в файл `errors.csv` с указанием номера строки и подробного текста ошибки.
- **FR-3.5: Приведение типов**  
  Корректная сериализация в целевой формат (числа как числа, а не строки в JSON; даты в формате ISO).

### 2.4. Подсистема отчётности (Reporters)
- **FR-4.1: Сводка в консоли**  
  Вывод понятной текстовой статистики:
  - Всего записей;
  - Успешно обработано;
  - Количество ошибок;
  - Детализация по строкам и полям;
  - Пути к сохранённым файлам (`output`, `errors`, `report`).
- **FR-4.2: HTML-отчет**  
  Генерация автономного HTML-файла (без внешних зависимостей/CDN):
  - Метрические карточки (Всего, Успешно, Ошибок, Процент качества);
  - Таблица распределения ошибок по полям;
  - Таблица распределения по типам правил;
  - Полный интерактивный журнал строк с ошибками.
- **FR-4.3: Команда `stats`**  
  Аналитический профилировщик структуры любого файла данных: количество записей, заполненность, количество пустых и уникальных значений, выведенный доминирующий тип данных, границы min/max.

### 2.5. Интерфейс командной строки (CLI)
Команды CLI:
- `databridge convert <input> --to <fmt> --config <schema> --output <output> [--errors <errors>] [--report <report>]`
- `databridge validate <input> --config <schema> [--report <report>] [--errors <errors>]`
- `databridge stats <input>`

## 3. Нефункциональные требования

- **NFR-1 (Платформа и язык):** Python 3.8+ (рекомендован ТЗ). Кроссплатформенная совместимость (Windows, Linux, macOS).
- **NFR-2 (Архитектура):** Без использования СУБД. Все операции осуществляются исключительно с файлами в памяти/потоке.
- **NFR-3 (Модульность):** Четкое разделение ответственности: `readers/`, `validators/`, `converters/`, `reporters/`, `cli/`.
- **NFR-4 (Надежность и обработка исключений):** Пользовательские ошибки (неверный путь к файлу, синтаксическая ошибка JSON/XML, несоответствие схемы) перехватываются и выводятся в понятной форме, исключая необработанные «сырые» stack trace.
- **NFR-5 (Тестируемость):** Покрытие модульными и интеграционными тестами (более 15 обязательных по ТЗ, в проекте реализовано 30+ тестов).
- **NFR-6 (Расширяемость):** Добавление нового формата данных (например, YAML, Parquet) требует только создания одного класса `Reader`/`Writer` без модификации движка валидации и трансформаций (принцип Open/Closed из SOLID).
