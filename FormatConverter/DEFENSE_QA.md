# Ответы на контрольные вопросы к защите проекта DataBridge

Данный документ содержит исчерпывающие и аргументированные ответы на 10 контрольных вопросов раздела 7 технического задания.

---

### Вопрос 1: Как вы организовали чтение разных форматов? Что общего у всех Readers?
**Ответ:**
Все модули чтения организованы на базе единого абстрактного базового класса `BaseReader` (паттерн **Template Method / Strategy**), расположенного в `databridge/readers/base.py`.
- **Что общего:**
  1. Единый контракт метода: `read(file_path: str, **kwargs) -> List[Dict[str, Any]]`.
  2. Все Readers приводят данные к общему внутреннему каноническому представлению — списку плоских словарей (`List[Dict]`), где ключами являются названия полей, а значениями — сырые данные.
  3. Все Readers обязательно обогащают каждую запись служебным полем `_row_number` (исходный 1-based номер строки), что позволяет точно локализовать ошибки при последующей валидации.
  4. Общая логика предварительной проверки существования и доступности файла (`validate_file_exists`).
  5. Единая система исключений — любое низкоуровневое исключение оборачивается в понятное пользователю `ReaderError` с указанием пути к файлу и причины.
  6. Создание экземпляров осуществляется через фабрику `get_reader(path)` на основе расширения или явного флага.

### Вопрос 2: Как добавить новый формат, не меняя остальной код?
**Ответ:**
Благодаря следованию принципу **Open/Closed Principle (SOLID)**, расширение системы новым форматом (например, YAML, TOML или Apache Parquet) не требует изменения существующего кода валидации, конвертации или CLI:
1. Создаётся новый класс в `databridge/readers/` (например, `YAMLReader`), унаследованный от `BaseReader`, реализующий метод `read()`.
2. Создаётся класс в `databridge/writers/` (например, `YAMLWriter`), унаследованный от `BaseWriter`, реализующий метод `write()`.
3. В словари `EXTENSION_MAP` в файлах `readers/factory.py` и `writers/factory.py` добавляется сопоставление расширения (например, `".yaml": "yaml"`).
4. Движок валидации (`ValidationEngine`), цепочки трансформаций, маппинг колонок и генератор отчетов начинают работать с новым форматом автоматически без единой правки.

### Вопрос 3: Как работает движок валидации? Как задаются правила?
**Ответ:**
Движок валидации (`ValidationEngine`) работает на основе декларативной схемы в формате YAML или JSON.
- **Задание правил:** Схема описывает массив объектов `fields`. Каждое правило задает ограничения: `required`, `type`, `min`/`max`, `min_length`/`max_length`, `pattern` (RegEx), `unique`, `allowed_values`.
- **Принцип работы движка:**
  1. Движок компилирует конфигурацию в типизированные структуры `FieldRule` и `ValidationConfig`.
  2. Валидация выполняется по записям (row-by-row). Для каждого поля записи вызываются чистые функции валидаторов (`rules.py`).
  3. Для правила `unique: true` движок накапливает значения в хэш-множествах (`Set[Any]`) по каждому полю, что гарантирует проверку уникальности со сложностью $O(1)$ на запись.
  4. По завершении проверки формируется неизменяемый результат `ValidationResult`, разделяющий исходный массив на `valid_records` и `invalid_records`, с прикреплением списка объектов `ValidationError`.

### Вопрос 4: Что происходит с некорректными записями? Почему вы выбрали именно такую стратегию?
**Ответ:**
- **Что происходит:** Некорректные записи отфильтровываются из основного потока данных, чтобы не нарушать целостность целевой системы, и сохраняются в отдельный файл `errors.csv` (по умолчанию) с сохранением всех исходных значений, номера строки и описанием конкретной причины ошибки. Кроме того, детали ошибок попадают в интерактивный HTML-отчет и выводятся в консоль.
- **Обоснование стратегии:**
  1. **Стратегия изоляции (Dead-Letter Queue / Quarantine):** В отличие от стратегии "fail-fast" (немедленное прерывание при первой ошибке), наш подход позволяет обработать 99% корректных данных пакета, не блокируя бизнес-процесс.
  2. **Удобство ручной корректировки:** Файл `errors.csv` легко открыть в Excel или текстовом редакторе, быстро исправить некорректные поля оператором и повторно прогнать через утилиту.

### Вопрос 5: Как реализован маппинг полей?
**Ответ:**
Маппинг полей реализован через выделенный компонент `FieldMapper` (`databridge/converters/mapper.py`):
1. Правила маппинга задаются в секции `mapping` конфигурационного файла (например, `birth_date: birthday`, `email: contact_email`), либо через свойство `alias` внутри описания конкретного поля в секции `fields`.
2. После успешной валидации и применения трансформаций `FieldMapper` заменяет ключи входного словаря на целевые: `new_key = self.mapping.get(old_key, old_key)`.
3. Колонки, не упомянутые в правилах маппинга, сохраняются под своими оригинальными именами, исключая случайную потерю данных.

### Вопрос 6: Какие граничные случаи вы протестировали?
**Ответ:**
В рамках тестового плана проверено более 35 сценариев, включая специфические граничные случаи:
1. **Полностью пустые файлы и файлы только со строкой заголовков:** Корректный возврат 0 записей без сбоев.
2. **Строки, состоящие только из пробелов:** Корректно отсеиваются правилом `required`.
3. **Числа на границе диапазонов:** Проверены пограничные значения `val == min` и `val == max` (включительно), а также `min - 1` и `max + 1`.
4. **Нестандартные разделители и кавычки в CSV:** Экранированные запятые внутри кавычек, переносы строк внутри текстовых полей, точка с запятой и табуляция.
5. **Разные форматы дат:** `YYYY-MM-DD`, `DD.MM.YYYY`, `DD/MM/YYYY`, а также невалидные календарные дни (например, `99-99-9999` или 31 февраля).
6. **Регистронезависимость булевых полей:** `true/false`, `1/0`, `yes/no`, `да/нет`.
7. **Кодировки файлов в Windows:** Автоматическое определение кодировок UTF-8, UTF-8 с BOM, CP1251 (Windows-1251).

### Вопрос 7: Как вы обрабатываете ошибки чтения файла (битый CSV, невалидный JSON)?
**Ответ:**
Все потенциальные точки сбоя защищены обработчиками исключений с преобразованием низкоуровневых системных ошибок в дружественные сообщения для человека:
1. **Невалидный JSON:** Перехватывается `json.JSONDecodeError`, пользователю возвращается точная строка и колонка синтаксической ошибки (например: `"Синтаксическая ошибка в JSON файле (строка 3, колонка 15): Expecting property name enclosed in double quotes"`).
2. **Невалидный XML:** Перехватывается `ET.ParseError`, выводится строка с незакрытым или поврежденным тегом.
3. **Отсутствие файла или отсутствие прав:** Проверяется перед открытием через `validate_file_exists()`, выдается понятное сообщение без падения в аварийный трейсбэк Python.
4. **Код возврата CLI:** В случае ошибок утилита завершается с кодом возврата `1`, что позволяет обрабатывать ошибки во внешних скриптах.

### Вопрос 8: Что показывает HTML-отчёт? Для кого он предназначен?
**Ответ:**
HTML-отчёт (`report.html`) — это наглядный аналитический документ:
- **Для кого:** Для операторов данных, руководителей учебных отделов, бизнес-аналитиков и специалистов службы контроля качества данных, которым неудобно работать в терминале.
- **Что показывает:**
  1. **Метрические плашки:** Общее количество записей, число успешных, количество отсеянных и расчетный процент качества датасета (% Quality / Success Rate).
  2. **Метаданные:** Исходный файл, целевой файл, путь к схеме, точное время генерации.
  3. **Сводные таблицы аналитики:** Распределение ошибок по полям (позволяет выявить самое проблемное поле) и по типам правил.
  4. **Таблица журнала дефектов:** Построчный перечень всех ошибок с номерами строк, исходными значениями и описанием несоответствия.
- **Особенность реализации:** Отчёт полностью автономен, стилизован чистым вшитым CSS без внешних CDN и шрифтов и открывается на любом компьютере без интернета.

### Вопрос 9: Как бы вы масштабировали утилиту на файл в 1 млн строк?
**Ответ:**
При работе с датасетами масштаба $10^6+$ строк текущий подход загрузки всего списка в оперативную память может потребовать слишком много RAM. Архитектура DataBridge подготовлена к потоковому масштабированию:
1. **Потоковые генераторы (Streaming / Iterators):** Замена возвращаемого типа `BaseReader.read` с `List[Dict]` на генератор `Iterator[Dict]`. Это позволяет обрабатывать CSV строка за строкой с фиксированным потреблением памяти $O(1)$ (не более 20–50 МБ RAM).
2. **Пакетная запись (Chunking):** Запись в `BaseWriter` чанками по 5 000 – 10 000 строк.
3. **Проверка уникальности на диске / фильтр Блума:** При проверке `unique` на 1 млн строк множество в памяти может занять сотни мегабайт. Решение — использование компактного вероятностного фильтра Блума (Bloom Filter) либо встроенного легковесного индекса на диске (SQLite `:memory:` или временный файл RocksDB/LMDB).
4. **Параллельная валидация (Multiprocessing):** Так как валидация записей (кроме unique) является независимой операцией, чанки данных можно валидировать параллельно на всех ядрах CPU с помощью `concurrent.futures.ProcessPoolExecutor`.

### Вопрос 10: Какие функции добавили бы в следующей версии?
**Ответ:**
Для версии DataBridge 2.0 запланированы следующие улучшения:
1. **Автогенерация схемы по файлу (`databridge infer-schema input.csv`):** Автоматическое построение `schema.yaml` на основе статистического анализа датасета.
2. **Кросс-полевая валидация (Multi-field / Conditional validation):** Правила вида *"если поле `type == 'juridical'`, то поле `inn` обязательно и должно состоять из 10 цифр"*.
3. **Поддержка бинарных аналитических форматов:** Parquet, Feather, Avro для работы в стеке Big Data.
4. **Интеграция с внешними справочниками:** Валидация по API (например, проверка существования адреса по ФИАС/КЛАДР, проверка ИНН по реестру ФНС).
5. **Веб-интерфейс (GUI / Web UI):** Легковесный локальный дашборд на FastAPI + Vue.js с поддержкой Drag-and-Drop загрузки файлов и визуального конструктора схем.
